# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ReLife is a personal agent built on the **Claude Agent SDK** (Python) that acts through MCP servers and **learns over time** (facts + reusable skills). It runs on the **Claude Code Max subscription**, NOT a metered API key — `ANTHROPIC_API_KEY` is intentionally unset and the SDK drives the logged-in `claude` CLI. Do not introduce code that requires an API key. See `PROJECT_CONTEXT.md` for the full design rationale, locked decisions, and current status — read it before making architectural changes. `MODULE_DEEP_DIVE.md` explains the reasoning module by module (M1–M16, with `file:line` references) and `HOW_IT_WORKS.md` is the plain-English guide; update both when an architectural change lands.

## Architecture

The flow is `cli.py` → `agent.build_options()` → `ClaudeSDKClient` (streaming). Each `do`/`chat` invocation wires together three pluggable pieces, all passed into `build_options`:

- **Permissions** (`permissions.py`) — `classify()` is a pure function returning `("allow"|"ask", reason)`; `make_permission_callback()` wraps it as the SDK `can_use_tool`. Autonomy model: auto-allow read-only tools, file writes **inside the workspace**, shell build/test/git (incl. `git push`), and ReLife's own MCP tools (`mcp__relife*`, `mcp__browser`). Always-ask for outward/destructive actions (the `_OUTWARD_SHELL` regex catches email senders **in both shells** — `sendmail`/`mail` *and* `Send-MailMessage` — uploads and non-GET web calls (`curl -X POST`, `Invoke-RestMethod -Method POST`, `-OutFile`), a download piped into an interpreter, remote shells (`ssh`/`scp`, `Enter-PSSession`, `Invoke-Command -ComputerName`), package publish, privilege escalation (`sudo`, `-Verb RunAs`, `Set-ExecutionPolicy`), and unrecoverable device ops (`mkfs`, `dd of=/dev/…`, `Format-Volume`)), writes outside the workspace, and any unrecognized tool (fail-closed default). **`gh` is verb-based and fail-closed** (`_gh_outward`, `_GH_READ`): *every* `gh` occurrence in the command — including inside `bash -c "…"`, after `time`/`xargs`, or a full path to `gh.exe` — must be a known read (`issue|pr list/view/status`, `pr diff|checks|checkout`, `search`, `status`, `run list/view`, …) or `gh repo create|clone` (the authorized build→create→push flow); anything else asks, and `gh api` auto-allows only a REST GET (no method + no `-f/-F/--input`, or an explicit `-X GET`; `graphql` always asks). **The workspace boundary binds the shell too, not just `Write`/`Edit`:** `_write_targets()`/`_delete_targets()` extract what a command redirects to, copies to, or deletes (`> f`, `tee`, `Set-Content`, `cp`/`mv`, `rm`, `Remove-Item`, `del`) and `_escapes()` asks when a target isn't provably inside the workspace — otherwise one redirect (`echo x > ~/.bashrc`) walked around the entire file-write policy. The extraction is deliberately heuristic (shell grammar isn't a regex) and errs toward asking: for deletes, a target we can't evaluate (`rm -rf "$DIR"`) counts as outside. Non-interactive runs **deny** ask-cases rather than block. **claude.ai connectors (Gmail / Google Calendar / Google Drive)** are the first real outward capability: they ride the logged-in subscription (no keys, no local server — the CLI attaches them to every session, `setting_sources=None` notwithstanding) and surface as `mcp__claude_ai_<Service>__<tool>`. Policy is **verb-based and fail-closed** (`_CONNECTOR_READ`/`_CONNECTOR_WRITE`): a name that says it reads (`search|list|get|…`, plus `authenticate`) auto-allows, a name that says it changes the world (`send|create|delete|modify|reply|…`) asks, a name that says neither asks, and the write check wins when both match — so the exact tool names Google ships don't matter. The approval prompt (TTY and UI card) shows the call's leading fields via `agent._tool_brief`, so the user approves a concrete recipient/subject, not a blank line. **Schedule grants** (`normalize_grants`/`grant_allows`, pure, same file) are the one sanctioned widening: a schedule may pre-approve `email` (Gmail send/reply/forward/draft) and/or `calendar` (create-event) **to listed addresses only**. They apply only to connector ask-cases (never file/unknown tools, and the shell only via the one bound `pull_request` shape below), exclude destructive ops even when the op also matches, require *every* address outside free-text fields (`body`/`subject`/`description`/…) to be on the list, fail on a recipient field holding a non-address, and for email need at least one visible recipient (a thread-inferred reply, raw MIME, a `draftId` send or `replyAll` ⇒ ask). The **one shell-shaped grant is `pull_request`**, valid only on a work schedule (`check_grants_fit`): stored unbound as `{"kind": "pull_request"}` (normalize drops any repo/branch a caller sends — an unbound grant matches nothing), bound per turn by `scheduler.bind_grants` to that issue's repo + branch, and then `_pr_create_matches` allows exactly one `gh pr create` tokenized with `shlex` (comments off): `--repo`/`--head` must equal the bound pair, only title/body/base/draft/fill flags, each at most once, no positional, and the raw command may contain no `$`/backtick (bash *and* PowerShell expansion) and no operator token (`; | & > < ( )`), so no chain, redirect, `--body-file` or reviewer ping rides along. `make_approval_callback(..., preauthorize=)` consults them after `classify` says ask and before the broker.
- **MCP servers** (`config.default_mcp_servers()`) — `browser` (Playwright via `npx @playwright/mcp`) and `relife_memory` (in-process SDK server). Memory is shipped as an MCP server *even though in-process* so the agent-facing contract is unchanged when it's later split out.
- **Memory hooks** (`hooks.py`) — a `UserPromptSubmit` hook auto-injects relevant recalled memories + skills + workflows before each prompt (and *reinforces* what it surfaces), de-duplicating across the three sources and capping total injected size (`RECALL_INJECT_BUDGET`); a `PostToolUse` hook journals every tool call to the event log; a `Stop` hook captures a deterministic **episode** (task intent + tool approach) for multi-step runs, feeding the recurring-episode→pattern detector even when the agent never calls `memory_save`. **The episode is scoped to the turn, not the session**: the event log is keyed by session id and a chat/server session runs many turns, so the prompt hook stashes the session's latest event id alongside the prompt and the Stop hook only takes events after it (otherwise every later episode replayed the whole session's tools). **All three hooks fail soft** — a memory error (daemon down, store error) degrades to no injected context / nothing captured, never an exception into the SDK. **Hooks and the memory MCP tools never touch the client on the event loop:** every sync client call goes through `memory.client.off_loop` (`anyio.to_thread`), because under `relife serve` one loop carries every session's stream and approvals — inline, each recall / journaled tool call / agent-requested consolidation froze them all. The agent benefits without explicitly calling recall.

**Per-task loop:** recall (hook injects memory+skills+workflows, reinforcing them) → act (tools, gated by `classify`, journaled to events) → reflect (agent calls `memory_save`/`skill_write`/`workflow_save`) → **consolidate** (a "sleep" pass after the run: decay/forget, dedupe, learn workflows from recurring tool sequences).

### Memory layer (`relife/memory/`) — cognitive model
Memory behaves like a brain: each item's relevance **rises when used** and **fades when ignored**, recall **fuses four signals**, and a consolidation pass periodically forgets and generalizes. The public `save`/`recall` API stays backward-compatible with v1.
- `cognitive.py` — **pure, deterministic, no I/O** heart of the model: ACT-R-inspired `activation()` (frequency + recency decay + importance), `fused_score()` (now takes optional `kind` for a small per-kind prior), `should_archive()`, and `should_hard_delete()` (the slow second forgetting tier). All tunables in `config.py`. NB: importance deliberately influences recall via *two* paths (it lifts activation AND is a direct signal) — documented in `config.py`.
- `store.py` — the store is an injectable **`MemoryStore(db_path)`** class; module-level `save`/`recall`/… are back-compat shims over a default instance bound to `_DB_PATH` (still a reassignable global tests rely on — the default is rebuilt when it changes). SQLite at `data/relife.db`; schema version tracked via **`PRAGMA user_version`** with ordered migrations (`_migrate_to_v2`, `_apply_migrations`). **Two-stage recall**: Stage 1 pulls bounded candidates from **FTS5** (+ the vector index when embeddings are on), Stage 2 fuse-ranks only those, then drops anything under `RECALL_FLOOR`. `save()` reinforces exact duplicates and (embeddings on) near-duplicate paraphrases; default importance is kind-based.
- `vector_index.py` — the **scalability seam** for semantic candidate search behind a `VectorIndex` protocol. `BruteForceIndex` (column scan, always correct, default) and a **soft-optional** `SqliteVecIndex` (`sqlite-vec` `vec0` table; `pip install -e ".[vector]"`). `get_index()` only returns the ANN backend after a runtime **self-test** passes — so an unavailable/misbehaving extension can never break recall.
- `embeddings.py` — **soft-optional** local semantic vectors via `fastembed` (ONNX, offline, **no API key**). `available()/embed()/cosine()`; everything degrades to keyword+activation if absent. Never a hard dependency; tests force it OFF (see `tests/conftest.py`).
- `service.py` / `client.py` — the **service seam**. `MemoryService` is the in-process facade (save/recall/forget/**archive(id)/get(id)**/consolidate/stats, skill_write/find/count, workflow_write/find/count, **and** log_event/events_for_task/event_count) over `MemoryStore` + the skills/workflows/events modules; `MemoryClient` is the consumer interface. `default_client()` picks the transport **by environment**: `RELIFE_MEMORY_URL` set → `HttpMemoryClient` against the standalone daemon; unset → `LocalMemoryClient` (direct in-process calls, the default — no daemon required). **Every** consumer — MCP tools, both hooks (recall *and* event/episode), the CLI — goes through `default_client()`, so the split changes only the transport, not consumers. Scope now covers long-term memory, procedural memory (skills/workflows), **and the tool-event log** — the whole consumer-facing surface. The skill/workflow/event service methods delegate to the module functions *at call time*, so they honour `_SKILLS_DIR`/`_WORKFLOWS_DIR`/`events._DB_PATH` reassignment (test isolation) and the daemon's binding. `consolidate()`/`dream()` are the only ops that stay module-level (they *mine* those defaults, which is why the daemon binds them rather than injecting a store).
- `remote/` — the **out-of-process transport** (Phase 2–3, optional `[daemon]` extra). `wire.py` is the dependency-free (de)serialization shared by both sides (`Memory`/`Skill`/`Workflow`/report ⇄ dict — the single source of truth; all string fields, so unicode round-trips losslessly). `daemon.py` is a FastAPI service core (`create_app`/`serve`) over the same `MemoryService`; **it binds the module-level `store._DB_PATH` and `events._DB_PATH`** via `_bind_db` (not an injected store) because `consolidate()`/`dream()` mine the module default — so all ops, upkeep included, hit one DB. It **likewise binds `skills._SKILLS_DIR` and `workflows._WORKFLOWS_DIR`** via `_bind_dirs` (Phase 3), for the *same* reason: `consolidate()` writes synthesized workflows via the `workflows` module functions (never the client — that would deadlock the daemon's own event loop), so those functions must resolve to the daemon's dirs. Memory routes also include `POST /archive` and `GET /memories/{id}` (id-addressed access for the inspection CLI — query-based `forget` archives *whatever matches best*, the wrong tool when the user points at one row). Skill/workflow routes are `POST /skills/write|find`, `GET /skills/count` (and `/workflows/*`); write handlers map `ValueError` → HTTP 400. Event routes are `POST /events/log`, `GET /events/by-task`, `GET /events/count` (events share the DB, so `_bind_db` already covers them — no dir binding). Quick handlers are `async def` calling the sync service on the loop; **bulk** ones (`/consolidate`, `/consolidate/maybe`, space copy/archive/export/import) run on a worker thread via `bulk()`, one at a time (`maybe` skips when one is running) — inline, one sweep froze every caller, `/mcp` agents included. The token compare is constant-time. `http_client.py` is `HttpMemoryClient` over a pooled keep-alive `httpx.Client`; it rebuilds real `Memory`/`Skill`/`Workflow`/`Event`/report objects so consumers see identical types, and re-raises the daemon's 400 as `ValueError` so both transports fail identically on invalid input. `dream` runs server-side (the `ask_model` callable can't cross the wire) with `timeout=None`, dispatched via `anyio.to_thread` since it's the one async method. A `relife.db.daemon` sidecar lets a stray in-process client **warn** (advisory, never refuse — a crash can orphan it).
- `skills.py` — single reusable procedures (Markdown+frontmatter under `data/skills/`). Behind the client seam (Phase 3): daemon-side when `RELIFE_MEMORY_URL` is set, else in-process.
- `workflows.py` — **multi-step** procedures (ordered chains of skills/actions) under `data/workflows/`, same file format as skills + a `trigger` field. Same client-seam routing as skills; `consolidate.py` still writes them via the module functions directly (it always runs where the data lives).
- `events.py` — tool-event log as an injectable **`EventLog(db_path)`** (own table in `relife.db`) with module-level shims; `_DB_PATH` reassignable for tests. Behind the client seam: the PostToolUse hook writes via `client.log_event` and the Stop hook reads one task's events via `client.events_for_task`, so events reach the daemon when `RELIFE_MEMORY_URL` is set. `consolidate.py` still reads the log directly (module-level) — it runs daemon-side under `POST /consolidate`, where `_bind_db` has bound `events._DB_PATH`.
- `rem.py` — the **opt-in "dream" pass** (`run_rem()`), the *only* LLM-driven memory path. Where consolidation is the cheap deterministic sleep, REM is the **manual, budget-gated** deep review the user triggers (`relife dream`): the model acts as an **adversarial critic** over a bounded "replay buffer" of recent memories (most-salient-first, watermarked in `data/rem_state.json`) checked against a reference frame of established knowledge. The model is an **advisor only** — its verdicts are applied here deterministically and **reversibly**: the sole destructive action is `archive` (never `delete`), the critic may **not** edit memory text (only `prune`/`reweight`), every verdict is **confidence-gated** (`REM_MIN_CONFIDENCE`) and bounded by a **prune cap** (`REM_MAX_PRUNE_FRACTION`), and every applied action is journaled to `data/rem_journal.jsonl` for audit/recovery. The model call is **injected** (`ask_model`, default `agent.ask_model_oneshot`) so the module stays SDK-free and the application logic is unit-tested with a stub. **Never auto-runs.**
- `consolidate.py` — the **"sleep" pass** (`run_consolidation()`, deterministic, LLM-free): (1) decay→archive via `should_archive`, then **hard-delete** long-archived rows via `should_hard_delete`; (2) dedupe near-duplicate memories (keyword Jaccard, plus semantic cosine when embeddings are on); (3) detect recurring episodes + recurring **action n-grams**, recording `pattern` memories; (4) synthesize a **workflow** from each *maximal* recurring sequence. N-grams run over **action labels** (`_action_label`: shell tools are categorized from their command — `git-clone`/`test`/`build`/… — not lumped as one `Bash`), and a **meaningfulness gate** (`_is_meaningful_seq`) only promotes sequences containing a distinctive action; pure editor/task motions (`Write→Edit`) are skipped, not turned into noise workflows. Auto-runs after a run when enough events accrue (`should_auto_run`, gated by `config.AUTO_CONSOLIDATE`); state in `data/consolidate_state.json`.
- `server.py` — MCP tools `memory_save` (now takes `importance`), `memory_recall`, `memory_forget`, `skill_write`/`skill_find`, `workflow_save`/`workflow_find`, `memory_consolidate`, `memory_dream` (the opt-in REM pass). Server `relife_memory` → `mcp__relife_memory__*` (trusted `mcp__relife` prefix → auto-allowed; **no permission changes**).
- `_text.py` — shared stopword tokenizer used by every keyword path.

### Agents and memory spaces (`relife/agents.py`, `memory/spaces.py`)
Memory is partitioned into **spaces** (store schema v3: `memories.space`/`source`, `events.space`; skills/workflows
under `data/spaces/<s>/{skills,workflows}`, the `default` space keeping the historical `data/skills|workflows` so no
files moved). `default` is the main agent's (the user's) memory — everything pre-spaces is there. An `AgentProfile`
(registry at `data/agents.json`, `AgentStore` with the `ScheduleStore` discipline: lazy, atomic, unreadable records
dropped, original kept aside) resolves to a `MemoryScope(read, write, source)`: it **writes only its own space**
(`space` or its name; never `default` — rejected at the record level) and **reads** own + `inherits` + `default`
(unless `isolated`). Handoff: `create_agent(inherit=…)` attaches parents' spaces read-only (flattened, so lineage is
transitive), `fork=` snapshots via `copy_space` (memories keep strength + provenance; skills/workflows copied unless
present), `promote` copies an agent's space into `default` (the only path in besides the main agent and an
explicit import), packs via `export_space`/`import_pack` (validated in full first; imports stamped `import:<space>`).
Attachments are read-only by design — a save can only land in one place, so agents that should share writes get the
same `space`. Tokens for HTTP MCP are `rla_…`, stored as sha256 only. **`ScopedMemoryClient`** (client.py) is the
enforcement point: its agent-facing methods take **no** space argument (passing one is a `TypeError`, not an
override), `forget`/`archive` reach only `scope.write`, admin ops (`copy/export/import/archive_space`) and `dream`
raise `PermissionError`. `memory_hooks(client)` / `memory_server(client)` / `config.default_mcp_servers(memory_client)`
bind one agent's scoped client; with no client they resolve the module's `default_client` at call time (tests
monkeypatch `hooks.default_client` / `memory.server.default_client`).

### Memory over MCP for any LLM (`memory/tools.py`, `memory/mcp_server.py`)
The memory tools are defined **once** as transport-neutral `ToolSpec`s (name, description, schema, async
`handler(client, args)`); `server.py` wraps `INTERNAL_TOOLS` as the in-process SDK server (names/schemas unchanged),
and `mcp_server.build_server` serves `EXTERNAL_TOOLS` (no `memory_consolidate`, no `memory_dream`; adds
`memory_context`, the same block the recall hook injects — `memory/context.build_context`) over the low-level `mcp`
`Server`: **stdio** (`relife mcp --agent NAME`, `--agent` required, unknown ⇒ exit 2) and **streamable HTTP** at
`/mcp` on the memory daemon (stateless + JSON responses; `McpHttpEndpoint` authenticates a registered agent's bearer
token — registry re-read per request, so revoke is immediate — and stashes that agent's scoped client in the ASGI
scope, which the tool handler reads back from `server.request_context.request`; DNS-rebinding protection via
`allowed_hosts_for(bind)`). The daemon's only lifespan runs the MCP session manager; REST routes still need none.

### Crews (`relife/crew/`, `[crewai]` extra)
`relife crew` = `planner.plan_crew` (one tool-less `ask_model_oneshot` call → JSON → `spec.normalize_spec`; one retry
with the validation error, then a single-ReLife-agent fallback) → `CrewRunRecord` (`data/crews/<id>/record.json`) →
plan shown + confirm → `build.ensure_profiles` (reuse existing agents, create new ones with the plan's inherit/fork —
**this is where memory is handed down**) → `build.build_crew` → `Crew.kickoff()` → per-task outcomes. Members:
`runtime: relife` → **`agent.ReLifeAgent(BaseAgentAdapter)`**, each task one fresh `ClaudeSDKClient` turn
(`turns.run_relife_turn`) in `<workspace>/crews/<id>/` with ReLife's permission callback, scoped hooks and scoped
memory server; `runtime: llm` → a CrewAI `Agent` on the model string (or `claude-max` → **`llm.ClaudeMaxLLM(BaseLLM)`**,
Claude via the CLI, no function calling ⇒ CrewAI's ReAct text, stop words applied by truncation) with ReLife memory as
in-process CrewAI tools (`memory_tools.py`, same specs) and the recall block prepended to its tasks — **no
machine-touching tools** (classify() can't gate CrewAI's loop). `spec.py`/`planner.py`/`record.py` are pure (no
CrewAI import); the turn runner and the LLM's model call are injected, so `tests/test_crew.py` runs a real
`Crew.kickoff()` with zero model calls. `runner.py` is `prepare_crew` (plan/validate + record `planned`) and
`execute_crew` (run a recorded plan), composed by `run_crew` for the CLI.

A plan reusing a **registered** agent never changes it: its `inherit` widens reads for that run only
(`build.run_scope`) — a plan is model output, and attaching is the user's act.

**Under the server** (`relife/server/crews.py`): `/crews` plans and runs crews, `/agents` + `/spaces` expose the
registry and handoff. A **`CrewHost`** is session-shaped — it shares the `EventStream` base with `AgentSession`
and is `SessionManager.adopt`ed — so SSE, the approval route, the UI's watch and the scheduler's recorder work on a
crew unchanged. `kickoff()` runs on a daemon thread; events hop back with `run_coroutine_threadsafe`; a member's
`can_use_tool` is `make_approval_callback` over a **`LoopBroker`** that hands each ask to the server loop's
`ApprovalBroker` (browser card; unattended ⇒ timeout ⇒ deny). Member `result`/`error` events are renamed
`member_done`/`member_error` so a crew has exactly one `result`. Stop denies pending approvals and the crew's
`task_callback` raises after the task in flight (covers CrewAI members too, not just ReLife turns).
Starts are reserved before
`adopt`'s first await (`_pending`) and run ids by `mkdir` (`CrewRunStore.reserve_id` — ids are
millisecond stamps, so two plans could share one). `CrewRunStore` retries `PermissionError` on read/replace — on Windows the worker's `os.replace` and a route's read
of the same `record.json` collide. A schedule may carry a `crew` spec (re-validated
against the live registry at each firing; no grants; not with `work`). `AGENT_MAX_CREWS` (default 1) caps running
crews; a running crew is never idle-reaped. Over HTTP a spec may only name `RELIFE_CREW_LLMS` + `claude-max`.

The system prompt uses the **`claude_code` preset** with `prompts/system.md` appended (persona + safety + memory/skill/workflow instructions). `setting_sources=None` deliberately prevents inheriting the surrounding repo's Claude Code settings.

### Work items (`relife/workitems.py`)
`relife work` works a GitHub issue end-to-end. Everything *around* the agent is deterministic and lives in `workitems.py` (unit-tested against a fake `gh` runner, zero model calls): `parse_ref` (`owner/repo#N`, issue URL, or `N` + `--repo`; a PR URL is rejected), `list_assigned` (`gh search issues --assignee @me`), `fetch` (body + last `MAX_COMMENTS` comments), `ensure_checkout` (clones to `<workspace>/<owner>__<name>` once; an existing checkout is **left untouched** — it may hold uncommitted work, so syncing is the agent's first, visible step), `branch_name` (`relife/issue-N-<slug>`, stable per title so a rerun resumes the branch), and `task_prompt`. **The checkout is the agent's workspace**, so the auto-allow write radius is that one repo. Issue text is written by third parties, so the prompt **fences it as untrusted data** (`<<<ISSUE … ISSUE>>>`, bounded by `BODY_LIMIT`/`COMMENT_LIMIT`); the permission policy is the backstop — branch + commit + `git push` are autonomous, `gh pr create` and any issue comment/close/edit ask. A closed issue exits 1 before anything is cloned. `run_gh` is looked up at call time (`run or run_gh`) so tests monkeypatch it.

### Build orchestration (`relife/build/`)
`relife build` scales to large projects the single-context `do` loop can't: it **decomposes → delegates → resumes**.
- `ledger.py` — `BuildLedger`: durable plan + progress at `data/builds/<id>/ledger.json` (+ a `plan.md` mirror). Source of truth for resume. Pure/deterministic.
- `server.py` — in-process MCP server `relife_build` (tools `build_plan_set`/`build_milestone_update`/`build_status`), bound to one ledger per run via closure. Surfaces as `mcp__relife_build__*` → already auto-allowed by the trusted `mcp__relife` prefix (no permission change).
- `agents.py` — the `builder` `AgentDefinition` the orchestrator delegates each milestone to via the **Task** tool, so each milestone runs in a *fresh context* (the orchestrator stays small). Parallel milestones are deliberately deferred.
- `orchestrator.py` — `run_build()`: wires ledger + server + builder + the `prompts/orchestrator.md` persona, streams the run, and persists `ResultMessage.session_id` so `--resume` continues the same session. Resume runs in the **ledger's own workspace** (not the CLI's default cwd) and re-injects the ledger state, so it's robust even if the CLI session is gone; a persisted `session_id` that **expired** across a Max session-limit reset falls back to a fresh session without losing milestone progress. In `cli.py`, `--resume` is a **boolean flag** (the positional arg doubles as the optional build id), so it no longer swallows the following option.
- `build_options` (agent.py) gained `system_prompt`/`agents`/`resume`/`max_budget_usd` params to support this; `do`/`chat` are unchanged.

### Always-on agent server + web UI (`relife/server/`)
`relife serve` (optional `[server]` extra: fastapi/uvicorn) turns the cold, one-shot `do`/`chat` loop into a **long-lived process** hosting persistent agent sessions, streaming their work to a **self-contained web UI** and routing outward-action approvals to the browser. Mirrors the memory daemon's patterns: a side-effect-free `create_app()` factory (ASGI-testable) + a `serve()` with lazy `uvicorn`, token auth (`GET /`, `/health` and `/auth/status` open), env vars in `config.py` (`RELIFE_AGENT_HOST`/`_PORT`/`_TOKEN`/`_APPROVAL_TIMEOUT`, plus the hardening knobs `_WORKSPACE_ROOT`/`_MAX_SESSIONS`/`_SESSION_IDLE_TIMEOUT`/`_MAX_QUEUED_TURNS`/`_MAX_MESSAGE_CHARS`/`_MAX_SUBSCRIBERS`/`_AUTH_MAX_ATTEMPTS`, default `:8600`).
- `agent.py` gained a pure **`to_event(msg) -> list[dict]`** — the single source of the streaming-message taxonomy (text / thinking / tool_use / **tool_result** / result), consumed by *both* the terminal `_render` and the server's SSE stream. `_render` now delegates to it (no CLI behavior change). **`tool_result` blocks arrive on a `UserMessage`**, not the assistant one (the CLI reports each result as a `user`-type frame — see the SDK's `message_parser`), so `to_event` walks both carriers; walking only `AssistantMessage` made the UI stream every tool *call* and never a result. Text on a `UserMessage` is the caller's own turn echoed back and is dropped (the server publishes that itself on submit).
- `session.py` — `AgentSession` owns one long-lived `ClaudeSDKClient` per session (kept open across turns, exactly as `run_chat` proves works); a worker task drains an inbound queue → `client.query` → `receive_response()` → `to_event` → publishes to SSE subscribers (with a bounded **ring buffer** for reconnect/replay by `Last-Event-ID`). `ApprovalBroker` routes each `classify()=="ask"` case to the UI (emits an `approval_request` event) and **blocks the run on an `asyncio.Future` until the browser decides or `AGENT_APPROVAL_TIMEOUT` elapses → deny** (same safe default as the non-interactive TTY path). `SessionManager` keys sessions by uuid. After each turn the worker awaits **`agent.maybe_consolidate_off_loop()`** — the pass runs on a worker thread (`anyio.to_thread`), because inline it stalled every session's SSE stream and every pending approval on the one loop for as long as the sweep took (seconds on a big store). Safe on a thread: each thread has its own SQLite connection (`memory/_sqlite.connect`) and `httpx.Client` is thread-safe. A process-wide non-blocking `threading.Lock` means two sessions finishing together don't sweep twice — the loser gets `None` and the throttle fires again next turn. A pass that changed something is published as a `note` event.
- `app.py` — `create_app(*, token, session_factory, workspace_root, reap)`; routes `GET /` (UI), `GET /health`, `GET /auth/status`, `POST /auth`, `POST /auth/logout`, `POST /sessions`, `GET /sessions/{id}`, `DELETE /sessions/{id}`, `POST /sessions/{id}/messages`, `GET /sessions/{id}/events` (SSE via `StreamingResponse`, no `sse-starlette` dep), `POST /sessions/{id}/approvals/{approval_id}`. **`GET /sessions/{id}` exists for the UI's reattach:** the page remembers its session id in `localStorage` and probes it on load, because unconditionally `POST`ing a session meant every reload spawned a second `ClaudeSDKClient` subprocess, orphaned the first until the idle reaper (an hour), lost the transcript, and after `AGENT_MAX_SESSIONS` reloads returned 429 with no way to clear it. Reattaching streams `?last_id=0` to replay the ring (a fresh page has no `Last-Event-ID` — that's per-`EventSource`; the route prefers the header, so automatic reconnects still resume rather than replay), and a header **"new session"** button `DELETE`s the current one so a slot can be freed from the browser. `session_factory` is **injected in tests** with a scripted/recording fake so the whole HTTP+SSE+approval flow is exercised with **zero model calls** (same discipline as `rem.ask_model`).
- `permissions.py` gained **`make_approval_callback(workspace, broker, *, timeout)`** — reuses the pure `classify()` verbatim (single policy source); the TTY `make_permission_callback` is untouched.
- UI is a **single self-contained `relife/web/index.html`** (vanilla JS + `EventSource`, theme-aware, no external assets) — ships in the wheel like `prompts/system.md`. **Concurrency model = the daemon's:** everything on one event loop; the suspended approval future and the resolving request interleave cleanly. Still single-user.
- **Scheduler (`schedules.py` + `scheduler.py`) — autonomous triggers on top of the server.** A schedule is a durable record (`Schedule`: name, task text, `spec`, confined workspace, enabled, `next_run_at`, bounded run history) in a JSON-file `ScheduleStore` at `data/schedules.json` (atomic tmp+`os.replace` writes; nothing written until the first change so `create_app` stays side-effect-free). Two spec forms, kept user-facing: `{"every": "30m"}` (interval, floored by `AGENT_SCHEDULE_MIN_INTERVAL`) and `{"at": "09:00", "days": ["mon","fri"]}` (daily at a *local* wall-clock time; `next_run()` works in naive local time and converts with `timestamp()` so 09:00 stays 09:00 across DST). Cadence logic is pure and takes an explicit `now`. `Scheduler` is one background task under the lifespan (like the reaper): every `AGENT_SCHEDULER_TICK` it fires each due (`enabled and next_run_at <= now`) schedule **as a turn submitted to a per-schedule `AgentSession`** — created in the schedule's workspace via the same `resolve_workspace` containment as `POST /sessions`, reused while alive, recreated after the idle reaper closes it — so a scheduled run streams, journals, learns, and asks for approval exactly like a typed turn (plus its schedule's **grants**, handed to *that turn only* via `AgentSession.submit(text, grants=)`, capped per turn by `AGENT_GRANT_MAX_USES`, every use published as an `approval_auto` event and listed in the run record's `acted`), and the UI's **watch** button attaches the console to it (the reattach path). **Nobody watching ⇒ an ask-case times out to deny**, the CLI's non-interactive rule; the submitted text carries a preamble telling the agent the run is automatic/unattended and to report a denial rather than retry (the UI renders that preamble compactly as `⏱ scheduled · name`). Policy: after *any* attempt the schedule advances from *now* (a slot missed during downtime fires once, never N×); a schedule whose session is still `busy` (new `AgentSession.busy`: a turn in flight or queued) is **skipped** for that slot rather than stacking turns; a run that can't start (session ceiling, full queue, bad workspace) is recorded as `skipped: …`/`error: …` and still advances — visible in its history, no tight retry. Routes: `GET/POST /schedules`, `GET/PATCH/DELETE /schedules/{id}`, `POST /schedules/{id}/run` (fire now; doesn't steal the regular slot) — mutating ones under the same auth+Origin guard; `AGENT_MAX_SCHEDULES` (429). Tests drive `Scheduler.tick(now)` against a fake manager and the routes with `run_scheduler=False` + a tmp `schedules_path`/`runs_dir` — never the real loop, never a model.
- **Work schedules — `relife work` on a cadence.** A schedule with `work` set (`{}` = any open issue assigned to the user, `{"repo": "o/n"}` / `{"label": "relife"}` narrow it; `normalize_work`, pure) has an optional `task` (extra instructions). Each firing, `Scheduler._prepare_work` runs the `workitems` plumbing **on a worker thread** (`asyncio.to_thread` — gh/git are blocking subprocesses and the loop is shared): list assigned → `pick_issue` (newest first, not in `schedule.worked`, label match) → fetch → `ensure_checkout` under the schedule's confined workspace. **No new issue ⇒ `skipped: no new assigned issues` before any session exists — an empty poll spends no Max budget.** A session's cwd is fixed at creation and each issue has its own checkout, so a work schedule **closes its idle session and creates a fresh one in the checkout** every firing. The issue ref is added to `worked` (bounded `MAX_WORKED`) only once the turn is actually submitted — a gh error or a full session ceiling leaves the issue available — and the history entry carries `item`. Unattended, `gh pr create` times out to deny, so the run ends with a pushed branch and the PR listed under "needed you". Turning `work` off by PATCH needs a task (validated together, assigned together); a corrupt `work` on disk loads as **disabled**.
- **Run outcomes (`runs.py`) — the unattended run must also *deliver*.** `submitted` only means the turn was queued, and the session it ran in is reaped an hour later, so the ring buffer must not be the only copy. For each firing the scheduler **subscribes to the session before submitting** and a recorder task collects exactly that turn's events (from the `user` echo whose text equals the scheduled prompt — a turn the user typed into the same session is not ours — to `result`/`error`, or `AGENT_SCHEDULE_RUN_TIMEOUT` → `timeout`, or shutdown → `interrupted`), then writes a `RunRecord` to `data/runs/<schedule>/<run_id>.json` (bounded per schedule by `AGENT_RUN_HISTORY`, removed with the schedule) and **upgrades the schedule's inline history entry** from `submitted` to the real status plus tool count, cost, denied count and a summary snippet. `summarize_events()` is pure: `summary` = the agent's closing text (everything after its last tool call — the prompt asks it to end with one), `denied` = every `approval_request` that resolved `False`, with the tool and brief so the user can do it by hand. Routes `GET /schedules/{id}/runs` (no events) and `GET /schedules/{id}/runs/{run_id}` (with events); the panel shows the last outcome on the card and a **runs** list with each run's summary and its "needed you — denied unattended" block. The recorder is a live subscriber, so the idle reaper never closes a session mid-recording; it unsubscribes when the turn ends.
- **`security.py` — the hardening policy, as pure functions** (same discipline as `memory/cognitive.py`: no I/O, no framework, unit-testable without HTTP or a socket): `token_matches` (constant-time), `presented_token` (bearer header **or** cookie), `same_origin` (CSRF), `guard_bind` (fail-closed bind), `resolve_workspace` (containment), `AttemptLimiter` (token-guess throttle). `app.py` only wires them to routes.
- **Auth covers the browser now.** `POST /auth` exchanges the token for an **HttpOnly, `SameSite=Strict`** cookie and every route accepts *either* carrier — because a browser `EventSource` **cannot set headers**, so without the cookie the SSE stream (which carries the whole transcript *and the approval prompts*) was the one route the UI could never authenticate. The UI asks for the token once (`GET /auth/status` tells it whether to), then rides the cookie. Bearer stays for programmatic clients. Mutating routes also require a same-origin `Origin` (a missing `Origin` = a non-browser client, allowed); failed `/auth` attempts are rate-limited per client address.
- **Session workspaces are confined to `AGENT_WORKSPACE_ROOT`** (default `./workspace`). `classify()` auto-allows writes *inside a session's workspace*, so an unconstrained path in the `POST /sessions` body would let the **caller choose the auto-allow blast radius**; `resolve_workspace` resolves first (so `..`/symlink escapes are caught) and rejects anything outside the root with a 400. The CLI's `--workspace` is deliberately unaffected — that's the local user speaking directly, not an HTTP body.
- **Everything unbounded is now bounded**, because the process is long-lived and each session owns a `ClaudeSDKClient` **subprocess**: `AGENT_MAX_SESSIONS` (429), an idle reaper (`AGENT_SESSION_IDLE_TIMEOUT`, started under the app **lifespan**) that skips sessions with a live SSE subscriber — the stream heartbeat `touch()`es the session, so a watching browser is never reaped mid-run — plus `AGENT_MAX_QUEUED_TURNS` (429), `AGENT_MAX_MESSAGE_CHARS` (413), `AGENT_MAX_SUBSCRIBERS` (429), and drop-oldest on a lagging subscriber queue (the ring + `Last-Event-ID` replay is how it catches up). Shutdown `aclose()`s every session so no subprocess is orphaned; `DELETE /sessions/{id}` closes one explicitly.
- **Still local-first (by design), but fail-closed:** `serve()` **refuses** to bind a non-loopback address without a token rather than warning — this process runs shell commands and edits files. There is **still no TLS and no multi-user model**, so exposing it beyond `127.0.0.1` means a token *and* a reverse proxy in front; treat that as a deliberate future step, not a supported configuration.

## Non-obvious constraints

- **A fresh memory DB stamps schema v2, not the current version.** `MemoryStore.init_db`'s `version == 0` branch
  builds the v2 table then lets `_apply_migrations` run every later step (v3 = spaces). Stamping `SCHEMA_VERSION`
  there skipped the new columns on fresh DBs. Each step is idempotent (column-exists checks).
- **Space semantics differ by layer, deliberately.** At the store, `spaces=None` means *unfiltered* (mechanism —
  consolidation and admin listings need every space); at the service/client, an agent-facing read with no spaces
  means the **`default` space** (pre-spaces behaviour), while `all_memories`/`count` default to every space. An
  empty `spaces` list matches nothing, never everything. Agents never choose: their scope comes from
  `ScopedMemoryClient`, and no MCP tool schema has a space property (a test enforces it).
- **Consolidation never crosses a space.** `_dedupe` groups by space, episodes and tool n-grams are mined per space,
  and patterns/workflows are written into the originating space — otherwise one agent's sweep could merge away
  another's memory or learn another agent's habits.
- **stdio MCP on Windows must warm the embedding model before serving.** With the stdio reader thread blocked in a
  read on the stdin pipe, constructing fastembed/onnxruntime on a worker thread deadlocked: `initialize` and
  `tools/list` answered, the first `tools/call` never did. `mcp_server._warm_up` loads it on the main thread first.
  Tests run with embeddings off, so only the release smoke (`RELEASE_TESTING.md`) can catch a regression.
- **`crew_tools` is outside the trusted prefix on purpose.** CrewAI tools handed to a `ReLifeAgent` are exposed as an
  SDK MCP server named `crew_tools` so each call is an unknown tool to `classify()` (ask). Never name it `relife_*`.
- **CrewAI's own memory, planning and knowledge stay off** (`Crew(memory=False, planning=False)`): they default to
  OpenAI embeddings/models and would demand a key; ReLife memory is the memory. Telemetry is off by default too.
- **`mcp` is a declared dependency, pinned `<2`.** ReLife imports it directly (`memory/mcp_server.py`), and the SDK
  alone allows `mcp<3`: a base install picked up mcp 2.3 (a restructured major) and the MCP tests failed to import
  in CI while every all-extras job — where CrewAI pins `mcp~=1.28.1` — passed. Porting to 2.x is a separate change.
- **Don't `asyncio.to_thread` code that calls `anyio.run`.** `to_thread` copies context variables, so anyio
  in the worker believes it is already inside the loop ("Already running asyncio in this thread"). The server's
  crew planner uses `loop.run_in_executor`, the crew itself a plain `threading.Thread` (the crew paths call
  `crew.turns.run_sync`, which is `anyio.run`).
- **Memory writers are untrusted, so writes are bounded at the store.** `MemoryStore.save` caps text
  (`MAX_TEXT_CHARS`) and tags, and `clean_importance` turns junk (`NaN`, `inf`, strings) into the kind
  default — `max(0, min(1, nan))` is **1.0**, so a NaN once meant "most important". Skill/workflow
  header values go through `_procedure.header_value` (one line, `---` defused): the parser ends the
  header at the first `---`, so a raw name could forge fields. Packs are checked for the same bounds
  in `validate_pack`, before anything is written.
- **Memory DB connections are cached per thread** (`memory/_sqlite.connect`, WAL + `synchronous=NORMAL`,
  `busy_timeout`). A connection per call made the open/close the cost (~15 ms per `log_event`,
  ~50 ms per save on Windows — a recall reinforcing 5 hits paid it 5×). Nothing closes them; sqlite3
  connections are per thread, so never hand one across threads. `close_all()` exists for tests.
- **Consolidation dedupe is indexed and incremental.** Keyword pairs come from prefix filtering
  (`_prefix`: exact for Jaccard ≥ 0.9, not a heuristic), meanings from stored embeddings through
  `_SemIndex` (only rows without a vector are embedded), and `dedupe_marks` in the consolidate state
  (`[id, created_at]` per `mode:space`, checked against the DB so a rebuilt DB can't skip memories)
  limits a pass to memories newer than the last. `tests/test_scaling.py` checks it merges exactly
  what the all-pairs loop did. Results: 3,000 memories 19 s → 0.2 s.
- **Skill/workflow search reads parsed files from a cache** (`_procedure.cached_dir`, keyed by
  mtime + size per file): opening files was the whole cost (~10 ms each on Windows, every prompt).
- **Reading never strengthens another space's memory.** `recall(reinforce_space=)` — the scoped
  client passes its write space — so an agent reading `default` or an inherited space (including via
  `memory_context` over MCP) leaves those memories' strength alone.
- **The event log is pruned and mined per space.** Consolidation keeps the newest `EVENTS_KEEP`
  (20k) events; pattern mining reads each space's own recent window (index `events_space`), and a
  turn's own events come straight off `(task_id, id)` (`events.for_task`) — a shared 500-event window
  let a busy agent hide everyone else's. The auto-consolidate throttle counts by `max_id()` (pruning
  lowers `count()`); an old state file's `last_event_count` is read as an id.
- **Registry writes re-read first.** `AgentStore.put/remove` reload the file under `_WRITE_LOCK` before
  writing (`put(new=True)` refuses a name taken meanwhile): routes run them on worker threads and a
  crew's worker creates agents, so a plain load→modify→write dropped concurrent writers' agents.
  Cross-process (CLI + server) this narrows the window; it is not a file lock.
- **CrewAI requires Python < 3.14** (1.15.x). The `[crewai]` extra is marker-gated; crew code that imports CrewAI
  (`llm`, `agent`, `native`, `memory_tools`, `build`) is only imported after `_crewai_or_exit()`.

- **`can_use_tool` requires streaming mode.** Use `ClaudeSDKClient` + `receive_response()`; the one-shot `query(prompt=str)` helper raises with a permission callback.
- **Windows console encoding.** `agent.py` reconfigures stdout/stderr to UTF-8 and uses `Console(legacy_windows=False)` — Rich otherwise crashes on glyphs like `→`/`✓` under cp1252.
- **Two shell tools.** On Windows the agent has both `Bash` and `PowerShell`; `permissions._SHELL_TOOLS` gates them identically. New shell tools must be added there.
- **`gh` on PATH.** `config.agent_env()` prepends the GitHub CLI install dir to the agent subprocess PATH only when `gh` isn't already resolvable (it was winget-installed mid-session).
- **Max session limits.** Live agent runs consume the same Max usage budget as interactive Claude Code. Prefer the deterministic test suite for verification; don't burn budget hammering live runs.
- **FTS5 external-content `COUNT(*)` lies.** `memories_fts` uses `content='memories'`, so `SELECT COUNT(*) FROM memories_fts` reads the *content table*, not the index — it can't tell you the index is empty. `store._init_fts` rebuilds based on whether the FTS table is being created for the first time (sqlite_master check), not on a count. FTS5 is also feature-detected: if the SQLite build lacks it, recall falls back to a full keyword scan.
- **Embeddings are soft-optional and forced OFF in tests.** `fastembed` isn't a hard dep. Tests stay deterministic (keyword + activation) regardless of whether it's installed: `tests/conftest.py` has an autouse fixture that monkeypatches embeddings off for every test **except** those marked `@pytest.mark.semantic` (which exercise the embeddings path and skip when `fastembed` is genuinely absent). Don't rely on the package merely being uninstalled. The candidate gate (keyword overlap **or** strong semantic sim) preserves the "unrelated query → nothing" guarantee even with embeddings on.
- **Consolidation must stay LLM-free.** `consolidate.run_consolidation()` is deterministic by design (cheap, safe to auto-run, testable). Don't add live model calls to it. The LLM-driven review lives in a **separate** module, `rem.py` (`relife dream`), which is *opt-in and never auto-runs* — that separation is the whole point. Guard tests assert `consolidate.py` never references the SDK/`ask_model` and that `rem.py` keeps its SDK import lazy.
- **The agent server's auth must work for `EventSource`.** A browser cannot set an `Authorization` header on an SSE connection, so the agent server accepts a cookie *as well as* a bearer token, and `GET /sessions/{id}/events` is gated like every other route. Don't "simplify" auth back to header-only — that silently reopens the transcript + approval stream to anything that can reach the port. Conversely, don't drop the `Origin` check on mutating routes: cookie auth is ambient, so a cross-site page could otherwise drive the agent.
- **The server's workspace root is a privilege boundary, not a convenience.** `POST /sessions` may name a workspace only *inside* `AGENT_WORKSPACE_ROOT`, because `permissions.classify()` auto-allows writes inside the session workspace. Widening it (or accepting the raw path again) hands the caller the auto-allow radius.
- **The auto-consolidate throttle decides + runs in one place.** `agent.maybe_consolidate` (CLI: `_maybe_consolidate`; server: `maybe_consolidate_off_loop`) calls `client.maybe_consolidate()`, which checks `should_auto_run()` (event-count vs. watermark) **and** runs the pass together on the memory side. Do **not** re-split this into a client-side `should_auto_run()` gate + a separate `consolidate()` call: under a daemon the gate would read the caller's (empty) local event log while the pass runs server-side, so auto-consolidation would silently never fire. Any "has enough accrued?" decision about server-side work belongs server-side — the same rule that keeps `consolidate`/`dream` mining module-level defaults.
- **The shell gate is a denylist, not a sandbox.** Any shell command not matched as outward / escaping / global-install is auto-allowed; inline interpreter code (`python -c`) or a script the agent writes can do anything the user can. `tests/test_permissions_corpus.py` holds the adversarial (`SHOULD_ASK`) and everyday (`SHOULD_ALLOW`) corpora — extend both when touching `permissions.py`, and nested shells (`bash -c`, `cmd /c`, `pwsh -Command`, `Start-Process -ArgumentList`) are re-classified on their inner command line.
- **Package installs outside the workspace ask.** A bare `pip install` / `python -m pip install` lands in the user's global site-packages (a release smoke run did exactly that); only a workspace venv interpreter, an activation in the same command, or `--target/--prefix` stays autonomous. `npm -g`, `cargo/go/pipx install` and OS package managers ask too. The system prompt tells the agent to use a project `.venv`.
- **Recall needs real relevance, not just activation.** Activation + importance alone clear `RECALL_FLOOR`, so the keyword gate is the only relevance check: a memory sharing ONE word with the query surfaces only if that word is distinctive (in ≤ `RECALL_COMMON_TERM_FRACTION` of active memories). Generic words ("write", "test") also name tools inside episode/pattern text, and the hook reinforces what it surfaces — without the gate, noise fed itself. Same reason consolidation treats the generic edit→test→commit loop as low-signal.
- **The claude.ai Gmail connector can send** (re-checked 2026-10-09 against the live schemas; an earlier note said it couldn't). It ships `send_message`, `reply`, `forward`, `create_draft`/`update_draft`/`delete_draft` plus read/label/trash/spam tools; Calendar ships `create_event`/`update_event`/`delete_event`/`respond_to_event`/`suggest_time`. Recipients are lists of plain addresses, content fields are camelCase (`htmlBody`, `forwardText` — `_snake()` normalizes them), attendees are `{email, …}`. Two fields reach people the visible recipients don't name, so an `email` grant never covers a call carrying them: `send_message(draftId=…)` sends the stored draft as-is (ignores `to`/`cc`/`bcc`), and `reply(replyAll=true)` keeps the thread's CC. Whether a send actually goes through also depends on the OAuth scopes the user granted when linking. `tests/test_grants.py` / `test_permissions.py::test_real_connector_tool_names` pin the real names and shapes.
